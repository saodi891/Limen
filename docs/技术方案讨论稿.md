# Forge 1.20.1 模组技术方案讨论稿

## 1. 技术讨论原则

后续讨论重心放在技术实现，而不是内容设定。

我会优先围绕以下问题追问：

- 代码结构如何设计。
- Forge 1.20.1 应该用哪个注册、事件、配置或数据系统。
- 世界生成和结构数据如何组织。
- Blockbench/GeckoLib 资源如何导入。
- 如何提高兼容性。
- 如何给数据包、整合包和其他模组留扩展点。
- 哪些选择会影响未来维护成本。

内容设定只在影响实现时追问，例如结构尺寸会影响生成算法，Boss 阶段会影响同步和动画，战利品性质会影响注册与数据包格式。

## 2. 基线方案

建议基线：

- Minecraft: Java Edition 1.20.1
- Forge: 47.x
- Java: 17
- Gradle + ForgeGradle
- 开发语言：Java
- 初始项目类型：单模块 Forge MDK 工程

项目名：

- 中文名：《门扉之外》
- 开发阶段称呼：《门扉之外：测试》

英文名与 Mod ID 已确定：

- 英文名：`Limen`
- Mod ID：`limen`

命名理由：`Limen` 短、好记，具有“门槛、边界、临界点”的含义，契合《门扉之外》“推开门扉、越过边界、进入未知”的核心主题，也适合公开发布后作为长期品牌使用。

包名建议：

```text
com.<author_or_team>.<modid>
```

说明：

- 包名是 Java 代码命名空间，不是玩家直接看到的名字。
- 通常由作者/团队标识 + Mod ID 组成。
- Mod ID 已采用 `limen`，包名可类似 `com.moonlightc.limen`。
- 作者/团队段可以后续确认，但公开发布前最好稳定。

## 4. 世界生成技术路线

第一阶段最终包含囚禁高塔和幽灵府邸，但当前实现顺序调整为先完成生物系统基础，再完成调用这些生物的结构。结构脚手架仍需按后续需求预留。

### 4.1 优先方案：原版数据驱动结构

尽量使用原版/Forge 结构数据系统：

- `data/<modid>/worldgen/structure/`
- `data/<modid>/worldgen/structure_set/`
- `data/<modid>/worldgen/template_pool/`
- `data/<modid>/worldgen/processor_list/`
- `data/<modid>/structures/`

优点：

- 数据包友好。
- 兼容整合包。
- 结构模板可由 NBT 文件管理。
- 生成参数可被数据包覆盖。
- 代码量更低，侵入性更小。

适合：

- 囚禁高塔和幽灵府邸目前确定为固定单体结构，并拥有多个变体。
- 结构逻辑主要由模板、战利品箱、刷怪笼、处理器和少量触发机制组成。

结构变体方案：

- 每个变体独立模板，例如 `prison_tower/normal`、`prison_tower/inverted`、`prison_tower/torture`、`prison_tower/winter`。
- 变体选择可由 biome tag、结构集、template pool 或自定义选择逻辑控制。
- 优先尝试数据驱动表达；如果需要“同一结构根据群系动态选变体”，可能需要少量代码辅助。

### 4.2 增强方案：自定义结构类

当结构需要复杂生成逻辑时再考虑自定义结构类。

适合场景：

- 结构形态需要根据地形动态变化。
- 结构需要复杂随机布局。
- 结构需要与周围环境做大量规则判断。
- 结构要生成特殊入口、封印、Boss 房间或多阶段状态。

代价：

- 代码复杂度更高。
- 数据包覆盖能力下降。
- 兼容和维护成本更高。

初步建议：

- 先按原版数据驱动结构设计。
- 只有当囚禁高塔或幽灵府邸的生成规则确实无法用原版结构系统表达，再补自定义结构逻辑。

当前已确认：

- 囚禁高塔：固定单体结构，多变体，主世界生成。
- 幽灵府邸：固定单体结构，多变体，主世界生成。
- 稀有度暂不讨论。

## 5. 生物系统技术路线

当前优先实现生物系统基础。

目标：

- 先打通 `Detector` / 探机的完整链路。
- 后续结构可以直接调用这些生物，而不是结构完成后再倒补实体系统。
- 为复杂动画、Boss、多阶段行为和结构专属生成预留接口。

基础链路：

- `ModEntities` 注册 `EntityType`。
- 实体类继承合适的原版基类，例如 `Monster`、`PathfinderMob` 或 Boss 专用基类。
- 在 Forge 事件中注册实体属性。
- 注册刷怪蛋或测试生成方式。
- 客户端注册 renderer/model/animation controller。
- 掉落走 loot table。
- 语言文件、模型资源、贴图资源和声音资源按规范组织。
- 配置控制实体是否启用、基础属性倍率、调试日志等。

第一个正式生物：

- 英文显示名：`Detector`
- 中文译名：探机
- 注册 ID：`pama_detector`
- 概念命名：用户提出为 `PAMA_detector`，代码和资源中按 Minecraft 规范使用全小写 `pama_detector`。
- 阶段定位：第一阶段 Boss 红石计算机 PAMA 的基础单位。
- 单位定位：工人/斥候。
- 基础运动：漂浮飞行移动。
- 空闲行为：缓慢随机漂浮。
- 索敌行为：使用骷髅级别的 16 格范围作为默认探测距离；存在仇恨目标时也会尝试锁定。
- 锁定规则：只锁定被不足两个探机锁定的玩家。
- 协同规则：每名玩家最多被两个探机锁定；两个锁定者以对称相位顺时针环绕。
- 发光规则：锁定后每 4 秒冷却一次；若目标没有原版发光效果，则施加 2 秒发光。
- 初版实现：使用飞行导航、无重力、随机悬浮移动、锁定玩家、环绕跟随和周期发光作为行为骨架。
- 攻击规则：探机无法正常攻击，不作为近战或远程直接伤害单位。
- 阵营标签：探机属于实体类型标签 `limen:redstone_machines`。
- 仇恨过滤：同属 `limen:redstone_machines` 的实体之间不产生仇恨。
- 扩展点：未来附魔、PAMA 造物联动、阵营判断应优先读取 `limen:redstone_machines` 标签，而不是硬编码实体 ID。

是否自然生成：

- 初版测试生物建议先不自然生成。
- 先通过刷怪蛋、命令或结构占位生成，避免在 AI 和动画未稳定时污染世界生成测试。
- 等结构与生物行为稳定后，再决定是否加入自然生成。

## 6. GeckoLib 采用建议

你已经明确需要复杂动画，因此我倾向正式采用 GeckoLib。

采用 GeckoLib 的影响：

- Gradle 需要加入 GeckoLib 仓库和依赖。
- `mods.toml` 需要声明依赖或可选关系，具体取决于是否强制前置。
- 实体类需要实现 GeckoLib animatable 接口。
- 客户端模型、渲染和动画 controller 要单独放在 client 包中。
- 资源导出采用 `.geo.json`、`.animation.json`、`.png`。

资源文件夹建议：

```text
assets/<modid>/geo/entity/
assets/<modid>/animations/entity/
assets/<modid>/textures/entity/
assets/<modid>/sounds/
```

Blockbench 交付建议：

- 保留 `.bbmodel` 源文件到项目外或 `art_source/` 目录。
- 导出给游戏读取的资源进入 `src/main/resources/assets/<modid>/...`。
- 模型名、动画名、贴图名全部小写加下划线。
- 每个实体建立一个资源清单，记录模型、贴图、动画、音效对应关系。

## 7. 结构配置方案

Forge 配置负责控制全局开关和数值，数据包负责覆盖结构数据。

建议配置项：

```text
worldgen.enablePrisonTower
worldgen.prisonTowerSpacing
worldgen.prisonTowerSeparation
worldgen.prisonTowerSalt
worldgen.enableGhostMansion
worldgen.ghostMansionSpacing
worldgen.ghostMansionSeparation
worldgen.ghostMansionSalt
worldgen.debugStructurePlacement
```

注意：

- 1.20.1 的结构生成参数本身通常在 JSON 中定义。
- Forge config 和 worldgen JSON 如何同步，需要谨慎设计。
- 如果想让配置实时影响结构生成，可能需要代码介入。
- 如果接受“配置影响新世界或新生成区块”，实现会简单很多。

我建议：

- 初版把结构参数写入 JSON/datagen。
- Forge config 先控制是否启用结构和调试日志。
- 结构间距、分离距离等参数优先让数据包覆盖。
- 如果后续明确要用 config 改间距，再写自定义加载/注入方案。

## 8. 结构内部内容方案

结构内部对象建议尽量数据化：

- 战利品箱：loot table。
- 刷怪笼：NBT 或结构后处理。
- 普通装饰：结构 NBT 模板。
- 可替换方块：processor list。
- Boss 房间：先放占位结构和标记方块，后续实现触发逻辑。

结构触发机制可选方案：

- 玩家进入结构范围时触发。
- 玩家打开特定容器时触发。
- 玩家破坏/激活特定方块时触发。
- 玩家接近 Boss 房间 marker 时触发。

技术上建议先定义“结构标记方块或数据标记”的规范，避免后续到处写坐标硬编码。

## 9. 动画与 GeckoLib 科普

你会用 Blockbench 制作模型、骨骼和贴图。代码侧通常有两条路。

### 7.1 原版实体模型路线

Blockbench 导出 Java entity model。

优点：

- 无额外前置。
- 兼容性高。
- 适合简单实体。

缺点：

- 骨骼动画能力弱。
- 多阶段 Boss 动画会很痛苦。
- 动画逻辑常常需要手写 Java。

### 7.2 GeckoLib 路线

Blockbench 使用 GeckoLib animated model 工作流，导出模型、动画和贴图资源，代码中注册 animatable entity/item/block。

常见资源：

```text
assets/<modid>/geo/*.geo.json
assets/<modid>/animations/*.animation.json
assets/<modid>/textures/entity/*.png
```

优点：

- 适合复杂动画。
- 支持待机、行走、攻击、施法、死亡、阶段切换等动画控制。
- Boss 表现力强。
- 和 Blockbench 工作流匹配。

缺点：

- 需要把 GeckoLib 作为依赖。
- 玩家也需要安装对应前置，除非未来采用打包方式且许可允许。
- 需要处理服务端和客户端加载隔离。

初步建议：

- 既然你明确需要复杂动画，技术路线倾向 GeckoLib。
- 但工程第一步仍可先搭建世界生成，不立刻接 GeckoLib。
- 等第一个实体进入实现阶段，再正式加入 GeckoLib 并建立资源导入规范。

## 10. 数据包友好与兼容策略

为了让数据包作者“总有办法”，我们应避免写死。

具体做法：

- 结构、结构集合、模板池尽量 JSON 化。
- 战利品走 loot table。
- 配方走 recipe JSON。
- 类别判断走 tags。
- 生物生成和结构生物群系尽量走 biome tags。
- 机制规则如果复杂，后续设计自定义 JSON loader。
- 可选联动代码放 `integration`，主逻辑不直接依赖第三方类。

## 11. 公开发布影响

公开发布会影响代码实现中的这些细节：

- `mods.toml` 必须规范。
- Mod ID 一旦发布后不宜更改。
- 注册名一旦进入存档后不宜随意更改。
- 配置项命名要稳定。
- 世界生成内容要考虑存档兼容。
- 需要测试 Dedicated Server。
- 需要清晰区分客户端和服务端代码。
- 需要中英文或至少英文占位语言文件，方便平台展示和国际用户理解。

## 12. 下一轮需要拍板的技术问题

为了开始生物脚手架，我建议下一轮只讨论这些技术问题：

1. 包名作者段使用什么，例如 `com.moonlightc.limen`。
2. GeckoLib 是否作为正式前置引入。
3. 第一个测试生物属于普通怪物、小 Boss，还是纯技术占位实体。
4. 第一个测试生物是否先只支持刷怪蛋/命令生成。
5. 测试生物需要哪些基础动画：待机、行走、攻击、受击、死亡、施法。
6. 是否现在就搭建 Forge 工程脚手架。
