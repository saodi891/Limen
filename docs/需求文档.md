# 《门扉之外：测试》Forge 1.20.1 模组需求文档

## 1. 当前已确认需求

本节用于记录已经讨论并确认的需求，后续每轮重要讨论都应追加或修订到这里，避免遗忘。

- 模组中文名确定为《门扉之外》。
- 开发阶段可称为《门扉之外：测试》，但这不是正式译名。
- 英文名确定为 `Limen`。
- Mod ID 确定为 `limen`。
- `Limen` 含义：门槛、边界、临界点，契合“推开门扉、越过边界、进入未知”的模组主题。
- 模组核心寓意：一切始于玩家探索的心，是玩家因好奇推开新征程冒险的门扉。
- 运行平台为 Minecraft Java Edition 1.20.1。
- 模组加载器为 Forge，优先面向 Forge 47.x。
- 开发语言为 Java，运行环境为 Java 17。
- 主题优先级：主要是奇幻魔法、冒险战斗；次要是工业科技、生存增强。
- 内容方向：基于原版世界观加入更多怪物、可挑战 Boss、对应战利品，以及它们所在或相关的结构。
- 参考方向：可参考 Goety 这类较成熟的奇幻冒险向 Forge 模组，但实现时仍以本模组自己的结构、机制和兼容性目标为准。
- 第一阶段最终目标仍包含世界生成与结构，但实现顺序调整为先完成生物系统基础，再完成调用这些生物的结构。
- 第一阶段必须加入两种全新结构：囚禁高塔、幽灵府邸。
- 囚禁高塔和幽灵府邸都属于固定单体结构，但会有多个变体；生成时可根据所在生物群系或随机性选择变体。
- 囚禁高塔变体示例：普通塔、倒悬之塔、拷问之塔、永冬之塔等。
- 两种结构都在主世界生成。
- 结构稀有度暂不讨论。
- 结构的详细生成逻辑由后续讨论确定。
- 生物需要复杂动画。用户会使用 Blockbench 制作模型、骨骼、贴图等资源，并以 `.png`、`.bbmodel` 或后续约定格式提供到项目资源文件夹。
- 模组计划公开发布，这会影响发布规范、许可、元数据、语言文件、兼容性测试和版本策略。
- 配置系统既要支持普通玩家调整，也要尽量不阻碍数据包作者通过 datapack 改规则。
- 后续讨论的重心应放在技术实现、代码结构、数据格式、资源管线、兼容性、脚手架、构建发布、API/联动设计上。
- 内容设定由用户主动提供；只有当设定会影响代码实现、数据结构、资源组织、生成规则或兼容性时，才主动追问。
- 每个大版本或阶段可以有不同的核心生物和核心机制；可以等实现到对应阶段时再细化。
- 第一阶段 Boss 为红石计算机 PAMA。
- 第一阶段第一个生物为 `Detector`，注册 ID 为 `pama_detector`，中文译名为“探机”。
- `Detector` 是红石计算机 PAMA 的基础单位，具备漂浮飞行移动能力。
- `Detector` 定位为 PAMA 的工人/斥候单位，而不是纯近战怪物。
- `Detector` 空闲时缓慢漂浮移动。
- `Detector` 在骷髅级别索敌范围内发现玩家，或存在仇恨目标时，会加速接近并尝试锁定。
- `Detector` 的技能为“锁定”：发现被不足两个探机锁定的玩家后，用眼睛锁定该玩家，并在移动时保持顺时针环绕跟随。
- 每名玩家最多同时被两个探机锁定；两个探机会以对称位置环绕。
- 已锁定玩家后，探机每 4 秒完成一次冷却；若目标玩家当前没有原版“发光”状态，则施加 2 秒发光。
- `Detector` 无法正常攻击，主要作为 PAMA 的耳目、工人和斥候存在。
- PAMA 会大量制造探机，用于探索世界中它未曾见过的生物和方块，并弥补自身作为红石计算机无法移动的缺点。
- 探机存在的战略目的之一是协助 PAMA 击败并利用尚未被捕获、尚未被精神控制的玩家。
- 探机会与其他 PAMA 造物产生联动。
- 探机属于“红石器械”标签；同属此类标签的怪物之间不会产生仇恨。
- “红石器械”标签后续可能被某个附魔读取，用于对该类怪物施加集体增伤加成。

## 2. 项目目标

本项目计划制作一款运行于 Minecraft Java Edition 1.20.1 的 Forge 模组。模组将扩展原版世界观下的奇幻冒险内容，重点包括结构生成、敌对生物、Boss、战利品、装备、特殊机制和可配置规则。

开发原则：

- 优先复用 Mojang 原版系统和 Forge 推荐 API。
- 尽量通过数据包、标签、配置、事件和注册系统扩展内容。
- 避免默认使用 Mixin、字节码注入或替换原版核心逻辑。
- 兼容整合包环境，减少对其他模组的硬依赖。
- 给玩家、服务器管理员、整合包作者留下足够配置空间。
- 为后续可选联动和公开 API 留结构空间。

## 3. 初版开发重点

第一阶段优先级：

1. 构思并确认英文名、Mod ID、包名等公开发布前不宜频繁更改的命名。
2. 搭建 Forge 1.20.1 工程脚手架。
3. 建立注册系统、配置系统、datagen 和客户端/服务端隔离基础。
4. 先实现生物系统基础，包括实体注册、属性注册、AI、动画管线、资源导入规范和配置。
5. 再实现世界生成基础框架。
6. 添加结构：囚禁高塔及其变体。
7. 添加结构：幽灵府邸及其变体。
8. 为结构生成提供配置项。
9. 为结构内部内容预留怪物、Boss、战利品、战利品箱、刷怪笼、谜题或机制扩展点。

结构实现时必须提前考虑它们后续会承载：

- 结构专属怪物。
- 结构 Boss。
- 特殊战利品。
- 战利品箱 loot table。
- 结构内方块、装饰和交互机关。
- 生成频率、距离、维度、生物群系、地形适配等配置。

## 4. 世界生成与结构需求

### 4.1 囚禁高塔

暂定定位：

- 奇幻冒险向结构。
- 可能承载被囚禁生物、守卫怪物、战斗房间、封印机制或高塔 Boss。
- 固定单体结构，但允许多个变体。
- 变体可根据生物群系或随机性选择。
- 已提出变体方向：倒悬之塔、拷问之塔、永冬之塔等。
- 仅在主世界生成。
- 生成逻辑待用户后续详细描述。

技术需求：

- 使用 Minecraft 1.20.1/Forge 推荐的结构注册方式。
- 结构数据尽量以 JSON/NBT/template pool 等数据驱动形式组织。
- 支持通过配置控制是否生成、生成间距、生成分离距离或等价参数。
- 支持通过数据包覆盖结构模板、战利品表、标签和部分生成规则。
- 结构内战利品使用 loot table。
- 结构内实体生成尽量通过结构处理器、刷怪笼、数据标记或后续机制实现，而不是硬编码到单一逻辑里。

### 4.2 幽灵府邸

暂定定位：

- 奇幻、幽灵、冒险战斗向结构。
- 可能承载幽灵类怪物、诅咒机制、探索房间、Boss 或阶段性奖励。
- 固定单体结构，但允许多个变体。
- 变体可根据生物群系或随机性选择。
- 仅在主世界生成。
- 生成逻辑待用户后续详细描述。

技术需求：

- 与囚禁高塔共用结构生成框架。
- 结构代码应支持多个结构类型扩展，而不是为每个结构复制一整套注册和配置逻辑。
- 支持独立配置开关和生成参数。
- 支持独立 loot table、结构模板、处理器、标签。
- 为后续氛围表现预留客户端粒子、音效和渲染触发点，但服务端逻辑不得依赖客户端类。

## 5. 生物与 Boss 需求

当前实现顺序调整为先完成生物系统基础，再完成调用这些生物的结构。

需求方向：

- 加入基于原版世界观扩展的新怪物。
- 加入可挑战 Boss。
- 怪物和 Boss 与结构、战利品、机制形成闭环。
- 每个阶段可拥有不同核心生物和核心机制。
- 第一阶段围绕红石计算机 PAMA 展开。
- `Detector` / 探机作为 PAMA 的基础单位，先用于打通第一阶段生物系统。

技术要求：

- 使用 `DeferredRegister` 注册实体类型。
- 使用原版 AI Goal 和 Forge 事件组合行为。
- 使用 loot table 管理掉落。
- 使用配置控制生命值、攻击力、生成开关、生成权重等平衡项。
- Dedicated Server 不加载客户端模型、动画和渲染类。
- 复杂动画优先考虑 GeckoLib，但需要先评估依赖成本和资源导出流程。
- `Detector` 的资源 ID 使用小写 `pama_detector`，避免 Forge/Minecraft 注册 ID 大写导致资源加载或数据包兼容问题。
- `Detector` 初版移动方式为无重力悬浮飞行。
- `Detector` 初版 AI 应实现锁定名额限制、对称顺时针环绕、发光冷却与发光状态判断。
- `Detector` 及未来 PAMA 造物应通过实体类型标签 `limen:redstone_machines` 约束阵营、仇恨过滤和后续附魔增伤逻辑。
- `Detector` 后续可扩展为侦测、警戒、召唤、联动 PAMA 结构或 Boss 战机制。

## 6. 美术资源与动画管线

用户负责制作美术资源，包括模型、骨骼、贴图、音效等。

预计资源来源：

- Blockbench 项目文件：`.bbmodel`
- 贴图：`.png`
- 可能的动画文件：取决于最终选择原版动画管线还是 GeckoLib。
- 音效：格式和采样要求后续确定，通常建议使用 `.ogg`。

需要进一步确定：

- 是否引入 GeckoLib 作为前置。
- Blockbench 导出格式采用 GeckoLib animated entity，还是原版 Java entity model。
- 资源文件夹约定。
- 命名规范。
- 是否需要为资源建立导入检查清单。

初步技术判断：

- 如果需要复杂骨骼动画、Boss 多阶段动画、攻击前摇/后摇、特殊技能动画，GeckoLib 更合适。
- 如果只做简单走路、攻击、待机动画，原版模型也可完成，但开发成本和表现力可能不理想。

## 7. 物品、战利品与装备需求

内容方向：

- 怪物和 Boss 掉落独特战利品。
- 战利品可进一步合成、强化、召唤、解锁机制或作为装备材料。
- 物品应服务于冒险战斗主题，同时可少量承载工业科技和生存增强方向。

技术要求：

- 物品注册使用 `DeferredRegister`。
- 配方使用 JSON/datagen。
- 战利品使用 loot table。
- 装备属性尽量使用原版属性系统。
- 冷却、耐久、消耗、范围、伤害等数值应配置化。
- 使用 tags 让其他模组和数据包更容易识别本模组物品。

## 8. 配置系统需求

必须提供玩家和整合包作者可修改的配置。

推荐配置文件：

- `common`：通用平衡项，例如结构生成、生物生成、物品数值、机制开关。
- `server`：随世界保存的规则，例如结构生成策略、Boss 难度、机制是否启用。
- `client`：粒子、音效、HUD、提示、视觉效果等客户端表现。

第一批配置建议：

- 是否生成囚禁高塔。
- 囚禁高塔生成间距或稀有度。
- 囚禁高塔生成维度白名单/黑名单。
- 囚禁高塔生成生物群系标签。
- 是否生成幽灵府邸。
- 幽灵府邸生成间距或稀有度。
- 幽灵府邸生成维度白名单/黑名单。
- 幽灵府邸生成生物群系标签。
- 是否启用结构内特殊怪物。
- 是否启用结构内 Boss。
- 战利品倍率或稀有物品权重倍率。
- 调试日志开关。

配置原则：

- 用 `ForgeConfigSpec`。
- 配置值必须有上下限。
- 高频逻辑避免每 tick 反复解析配置。
- 明确哪些配置需要重启游戏、重启服务器或新建区块才生效。

## 9. 数据包友好要求

用户希望支持数据包改规则；实现上至少不能刻意制造障碍。

技术原则：

- 配方、标签、战利品表、语言、模型、方块状态尽量数据化。
- 结构模板、结构池、处理器列表、战利品箱尽量走原版数据系统。
- 不把生物群系判断、维度判断、战利品内容全部写死在 Java 代码里。
- 通过 tags 表达类别，而不是硬编码单个物品或方块。
- 对复杂机制，如果 Java 必须参与，也尽量设计 JSON 规则加载器或可扩展接口。

## 10. 兼容性要求

兼容性是基础要求。

- 默认不使用 Mixin；如后期必须使用，需要单独记录原因和影响范围。
- 不覆盖原版注册对象。
- 不替换原版行为入口。
- 不硬编码其他模组类。
- 可选联动通过 `ModList.get().isLoaded(...)`、tags、capabilities、IMC 或事件隔离。
- 网络包只发送必要数据，做方向和权限校验。
- Dedicated Server 不引用客户端模型、渲染、动画类。
- 世界生成必须避免过重计算。
- 结构生成不能导致区块生成显著卡顿。

## 11. 可选联动与 API 预留

可选联动方向：

- JEI/REI：展示机制、配方、战利品线索。
- Patchouli：游戏内手册。
- Curios：饰品类战利品。
- Jade/The One Probe：显示结构机制、方块状态或实体信息。
- Create：如果后续工业科技内容成型，可做加工链联动。

API 预留方向：

- 自定义事件：Boss 生成、Boss 击败、结构激活、机制触发。
- 接口：可作为仪式材料、可被结构机制识别、可参与特殊掉落计算。
- 标签常量：结构相关方块、可献祭物品、可被某类怪物识别的物品等。
- 数据驱动规则：结构内刷怪规则、战利品权重扩展、机制触发条件。

初版不承诺稳定公开 API，但代码结构要避免把未来扩展点写死。

## 12. 发布目标

模组计划公开发布。

发布相关要求：

- 准备 `mods.toml` 元数据。
- 准备中英文语言文件，至少中文必须完整；英文是否完整待确认。
- 准备 README、许可协议、更新日志。
- 规划 CurseForge/Modrinth 发布元数据。
- 版本号建议从 `0.1.0` 开始。
- 公开发布前必须测试客户端、服务端和常见模组共存。

## 15. 2026-07-27 实现补充记录

- 受控制骷髅 `skeleton_chipped` 已补充两条机制：
  - 死亡时额外概率掉落 `0-1` 个 `damaged_chip`
  - 头部接触水时按一次性脱控处理，概率掉落 `0-1` 个 `damaged_chip`，随后转化为原版骷髅
- 机械骷髅继续归类为 `limen:redstone_machines`，并保留“不穿护甲、不左撇子、不生成蜘蛛骑士、白天不燃烧”的约束
- 第三个生物确定为 `autonomous_spider`，中文名“机械蜘蛛”
- 机械蜘蛛当前第一版技术实现已确定的基础规则：
  - 归类为 `limen:redstone_machines`
  - 基础属性为 `24` 点生命值、`10` 点护甲值
  - 死亡后尝试在原地放置方块 `autonomous_spider_remains`（机械蜘蛛残骸）；若当前位置无法放置，则掉落对应方块物品
  - 拥有技能 `skill1`：冷却 `10s`，进入短前摇后释放以自身为中心、半径 `5` 格的脉冲
  - 脉冲会对范围内玩家施加自定义状态效果 `shocked` / “震撼”，默认持续 `3s`
- “震撼”第一版按真正的自定义效果实现，而不是复用原版减速：
  - 玩家受影响时无法正常移动
  - 玩家视场角会缩小
  - 该效果和数值已预留到配置系统中，后续可以继续细化
- 机械蜘蛛残骸当前使用兼容优先的占位方块实现，后续可替换为正式模型、贴图、碰撞箱与交互逻辑
- 当前这三类生物与“震撼”效果都已接入现有注册体系、语言文件、创造栏和基础资源路径
